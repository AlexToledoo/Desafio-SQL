# Desafio SQL — VemData

## 📌 Sobre o projeto

Este projeto foi desenvolvido como parte do desafio **VemData**, proposto pela **Growdev em parceria com a Edenred**.

O objetivo do desafio foi colocar em prática os conhecimentos de **SQL** e trabalhar com um banco de dados real, realizando consultas, análises e tratamento das informações disponíveis.

Para realizar o desafio, utilizei o banco de dados **Brazilian E-Commerce Public Dataset by Olist**, disponibilizado no Kaggle.

## 🗃️ Banco de dados

O banco utilizado foi o:

**Brazilian E-Commerce Public Dataset by Olist**

O dataset contém informações de um e-commerce brasileiro, incluindo dados sobre:

* Clientes
* Pedidos
* Produtos
* Vendedores
* Pagamentos
* Avaliações
* Itens dos pedidos
* Categorias de produtos
* Localização dos clientes e vendedores

Essas informações permitiram trabalhar com diferentes tabelas e relacionamentos, simulando situações mais próximas das encontradas no dia a dia da área de Dados.

## 🎯 Objetivo do desafio

O principal objetivo foi desenvolver consultas SQL para responder às questões propostas pelo desafio, utilizando os dados disponíveis no banco.

Durante o projeto, foram trabalhados conceitos como:

* `SELECT`
* `WHERE`
* `GROUP BY`
* `ORDER BY`
* `JOIN`
* `CASE`
* Funções de agregação
* Tratamento de dados
* Filtros
* Classificação de informações
* Análise dos resultados

## 🔎 Desenvolvimento

O desafio foi dividido em diferentes blocos de atividades, nos quais fui desenvolvendo as consultas SQL de acordo com as perguntas propostas.

Além de buscar os resultados, também foi necessário entender a estrutura das tabelas e analisar como os dados estavam organizados para conseguir realizar os relacionamentos e chegar aos resultados esperados.

## ⚠️ Desafios encontrados

Durante o desenvolvimento, encontrei algumas situações que tornaram o desafio mais interessante e também mostraram alguns problemas que podem acontecer quando trabalhamos com dados reais.

### Falta de chave primária ligando as tabelas

Algumas tabelas não apresentavam uma `PRIMARY KEY` ou um relacionamento tão claro entre elas.

Isso exigiu uma análise maior da estrutura do banco para entender quais colunas poderiam ser utilizadas nos `JOINs` e como as informações se relacionavam.

### Inconsistência no formato das colunas

Também encontrei diferenças na forma como alguns dados estavam armazenados.

Isso aconteceu principalmente com informações relacionadas a:

* Datas;
* Números;
* Valores booleanos.

Essas diferenças acabaram dificultando algumas operações e exigiram mais atenção durante a construção das consultas.

### Dados faltantes

Algumas colunas possuíam dados ausentes ou valores nulos.

Foi necessário considerar essas situações durante as consultas para evitar resultados incorretos e entender melhor o comportamento dos dados.

## 📚 Minha experiência

O projeto trouxe um desafio muito bom para ter uma visão mais próxima de como pode ser o dia a dia de uma pessoa que trabalha na área de **Dados**.

Consegui ter uma visão diferente dessa área, principalmente porque antes desse projeto eu não tinha tido muito contato com esse tipo de atividade.

Durante o desenvolvimento, precisei recorrer algumas vezes ao **material de apoio e ao glossário das aulas** para entender melhor alguns conceitos e conseguir avançar nas questões.

Isso acabou sendo uma parte importante do aprendizado, porque além de praticar SQL, também precisei aprender a analisar os dados, entender a estrutura das tabelas e pensar em como chegar ao resultado de cada problema.

No final, o desafio mostrou que trabalhar com Dados não envolve apenas escrever uma consulta SQL. Também é necessário entender os dados, identificar problemas, verificar os relacionamentos entre as tabelas e tomar cuidado com informações faltantes ou inconsistentes.
